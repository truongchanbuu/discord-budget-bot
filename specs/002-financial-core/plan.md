# Implementation Plan: Financial Core and Domain Invariants

**Feature**: `002-financial-core` | **Date**: 2026-11-12 | **Spec**: [spec.md](spec.md)
**Git branch**: `001-project-foundation` (unchanged); Spec Kit resolves the feature via its selector.
**Status**: Implemented and verified locally on 2026-11-12 under the maintainer's $speckit-implement instruction. This plan records the adopted design; [tasks.md](tasks.md) records delivery evidence.

## Summary

Add pure financial value/invariant validation to the existing package. VND quantities are exact
whole đồng in 0–18,446,744,073,709,551,615 inclusive; fresh changes are positive and virtual balances
cannot go below zero. A canonical constructor provides explicit invalid-input rejection.

A pure application function compares caller-supplied prior validated context before checking
fresh spending capacity. It returns an owned new candidate or borrowed replay, never changes a
balance, posts a journal entry, or guarantees durable/concurrent idempotency. Preserve origins
and separate handoff/manual-confirmation meaning from unavailable bank verification.

**Scale/Scope**: One validation call at a time with explicit prior context; future callers own

## Ownership and Public Boundary

Expose features::financial_core as an explicit application-facing facade. Re-export required
value/input/result/error types plus validate_intent; keep domain and application modules private.
Other features must use this facade, never reach into domain files. Re-exported values are
contract vocabulary; financial workflow decisions enter through validate_intent.

The dependency direction is lib → feature facade → application → own domain. Domain depends
only on std and thiserror. Existing main/bootstrap/config remain independent of this core;
no domain demo or new command is added to the executable. No changes to local comments/tooling
are included. Follow the user's brief tagged-comment rule for any necessary future comments.

Money, references, BalanceChange, VirtualBalance, and ValidatedChange encapsulate their invariants.
FinancialIntent is a named-field record of validated components, without a redundant builder/DTO.
A candidate owns its intent to preserve provenance if the caller later changes its input record.
New validation may clone those owned references once; replay borrows the prior candidate.
No raw mutable field/public constructor can forge a ValidatedChange.

## Value and Validation Design

Detailed field/API rules are authoritative in [data-model.md](data-model.md) and
[contracts/financial-core.md](contracts/financial-core.md). Core choices:

- Money stores private u64 whole đồng, accepts exact VND and canonical ASCII amount text;
  construction rejects negatives, decimal precision, unsupported currency/format, and overflow.
- Use all of u64's nonnegative range, not an arbitrary business cap. Arithmetic uses checked
  operations; virtual decrease maps underflow to InsufficientFunds. Future storage must preserve
  the full range or revisit its schema explicitly, never silently narrow.
- OwnerRef/TargetRef/OriginRef/IdempotencyKey are distinct nonblank owned reference types, compared
  exactly without silent trimming/case normalization. Shared nonblank checks are a domain rule,
  not a generic identifier abstraction. No generation, authentication or length policy is invented.
- BalanceChange enforces positive amount and named direction. VirtualBalance stays distinct from
  Money or bank funds; preview returns a fresh virtual value with no side effect.
- CompletionBasis permits HandoffOnly and ManualConfirmation. No BankVerified variant or claim.
- Prior context is Option<&ValidatedChange>. Only earlier successful validation can construct a
  coherent candidate. Callers assert acceptance; the object is not a durable receipt or trusted proof.
- Errors are categorical; no raw values in Display/Debug/source chains. Sensitive objects have
  redacted Debug or no Debug; no monetary Display or core tracing. Explicit accessors are deliberate
  value access and never automatic permission to log financial data.

### Validation order

1. Construction has already checked quantity, positive change, and nonblank reference invariants.
2. With prior context, compare owner/key first; reject generic context mismatch without details.
3. Same owner/key: compare every semantic field; changed meaning is IdempotencyConflict.
4. Exact match: return Replay borrowing prior candidate; ignore today's balance/capacity.
5. With no prior context, reject HandoffOnly as insufficient completion basis.
6. Preview the balance change with checked arithmetic; return Eligible with owned coherent intent,
   before and proposed balances. Never store or apply it.

No prior-context lookup occurs. None means only caller-supplied absence; separate validators can
both return Eligible. Future real commits must atomically enforce effect, origin, idempotency and
audit history. Awareness-before-handoff and trusted bank evidence remain future workflow duties.
